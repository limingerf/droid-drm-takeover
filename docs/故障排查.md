# 故障排查

先跑体检，它会告诉你大部分问题：

```sh
# 安卓侧
su -c 'sh /data/local/drm-takeover/core/switch.sh doctor'

# 容器侧
sh core/switch.sh doctor

# 当前状态
sh core/switch.sh status
```

日志位置：

| 侧 | 路径 |
|---|---|
| 安卓 | `/data/local/drm-takeover/run/logs/` |
| 容器 | `/root/droid-drm-takeover-logs/` |
| KWin 的 atomic 记录 | 安卓侧 `run/logs/kwinatomic.log` |
| 综合 journal | `run/logs/journal.log` |

Linux 应用里有「打开日志目录」按钮，不用记路径。

## 进不去 Linux

### `composer 仍持有 card0` / atomic 提交返 `-13 (EACCES)`

**根因**：`stop` 不动 `class hal`，而 composer HAL 属于 `class hal`。
必须**点名**停它。

```sh
adb shell su -c 'getprop | grep -i composer'          # 找服务名
adb shell su -c 'ls -l /proc/*/fd 2>/dev/null | grep card0'   # 看谁还持有
```

判据是 **composer 从 card0 持有者列表里消失**，不是 `init.svc` 变 `stopped`。

如果你设备的 composer 服务名不是 `vendor.qti.hardware.display.composer`，
改 `core/device/<codename>.sh` 的 `DEV_COMPOSER_SVC`。

### `Droidspaces 不可用`

```sh
adb shell su -c 'ls -l /data/local/Droidspaces/bin/droidspaces'
adb shell su -c '/data/local/Droidspaces/bin/droidspaces show'
```

没装的话本项目无法工作 —— 它依赖容器提供 Linux 用户态。
装好后确认 `DEV_DS_BIN` / `DEV_DS_CFG` 指对了。

### `容器里没有 .../linux/session-up.sh`

仓库没同步进容器。检查共享目录：

```sh
adb shell su -c 'ls /mnt/Droidspaces/drm/root/'
```

空的话说明 `ds_require_shared` 失败（容器没起来或共享目录没挂）。

### `kwin 没有持有 /dev/dri/card0`

KWin 起来了但没拿住屏。看 `kwinatomic.log`，然后：

```sh
# udev 记录写对了吗（KWin 的 Hardware 白名单只收 i915/amdgpu/nouveau/vmwgfx）
grep -r DRIVER /run/udev/data/ 2>/dev/null

# split 几何对吗
bin/kwinwrap --probe-split
```

## 屏幕不对

### 花屏

split 几何错了。`kwinwrap` 需要知道用哪两个 plane 各推半屏。

```sh
bin/kwinwrap --probe-split
```

stderr 里会列出**候选 plane**。核对后人工固定：

```sh
KWINWRAP_SPLIT_PLANES=<左>,<右> bin/kwinwrap --probe-split
```

如果自动发现失败，`kwinwrap` 会在日志里大声告警并说明它在用编译期的兜底值
（那是 piano 的常量，在别的设备上几乎肯定错）。**看到那个告警就一定要人工指定。**

### 面板有 mode，但整屏纯黑

最常见的原因：**`kactivitymanagerd` 没起来**。

plasmashell 硬依赖它，而它不会可靠地被 dbus 自动激活。
激活超时的话 plasmashell 会直接 `Aborting shell load`，
现象就是"kwin 活着、触摸在收、面板有模式，但整屏纯黑"。

```sh
grep -i 'aborting shell load' run/logs/*.log
```

`core/lib/display.sh` 的 `drm_start_desktop()` 会显式拉起它并等
`org.kde.ActivityManager` 上总线（还要给 `QT_QPA_PLATFORM=wayland`，
否则 Qt 找不到平台插件又自杀）。

### 完全没亮（连背光都没有）

安卓的关机流程会把 connector 的 `brightness` 写成 0，而 KWin **从不知道**
这个属性存在，永远不会写回。

```sh
ls /sys/class/backlight/                       # 找节点名，填 DEV_BACKLIGHT
cat /sys/class/backlight/*/brightness
```

`display/keepbright.sh` 会每 5 秒回写一次。确认它在跑：

```sh
ps | grep keepbright
```

如果 `DEV_BACKLIGHT` 留空且 `sysfs` 里没有 backlight 节点，
`kwinwrap` 会退回直接写 DRM connector 的 `brightness` 属性
（靠 `KWINWRAP_BRIGHTNESS`）。

### 画面在动但屏幕黑

和上面同一类问题（背光被反复写 0）。`keepbright.sh` 就是为这个存在的。

### 整屏纯黑，但 kwin / plasmashell 都活着、面板有 mode

**KWin 把合成器自己持久化禁用了。** 它的 OpenGL 场景只要初始化失败一次
（典型日志 `kwin_scene_opengl: couldn't find dev node for drm device` /
`kwin_core: Failed to open drm node: ""`），就会把

```ini
[Compositing]
Enabled=false
```

写进 `$DESKTOP_HOME/.config/kwinrc`。之后哪怕 DRM / EGL / 权限全部恢复正常，
它也**永远不再合成** —— 扫描出去的缓冲全是 0，就是纯黑。

```sh
# 直接看残留
grep -A2 '^\[Compositing\]' /home/<桌面用户>/.config/kwinrc
```

`core/lib/display.sh` 的 `drm_start_kwin()` 现在每轮接管前会把这个残留整行删掉
（只动 `[Compositing]` 段里的那一行，不碰别的配置），日志里会打
`清掉 kwinrc 里残留的 [Compositing] Enabled=false`。

### 画面是密集彩色竖条纹 / 噪点

**kgsl 的 OpenGL 路径在产出垃圾**，不是 DRM 接管的问题。

判据（重要）：把 KWin 的输出缓冲导出来看，如果**每 4096 字节只有几十字节有效数据**，
那就是 GL 侧写坏了；接管链路本身没问题。

```sh
# 先看 KWin 用的是哪个 fb
bin/kmsdump /dev/dri/card0 | grep '^PLANE '
# 再导出（注意必须按 fb 的真实 fourcc 解码，见下面的坑）
bin/fbdump /dev/dri/card0 <fb_id> /root/fb.ppm
```

解法是整条桌面链路改走软件渲染（设备层已经默认这么配）：

```sh
DEV_KWIN_ENV="KWIN_COMPOSE=Q"          # KWin 软件合成
DEV_QT_QUICK_BACKEND="software"        # Qt Quick 软件渲染
```

只设前者的话 plasmashell 仍会去要 OpenGL 2，失败会弹一个
「Plasma 启动失败：无法正常调用 OpenGL 2 或备用的软件渲染器」的对话框然后退出。

> ⚠️ **`fbdump` 必须按 fb 的真实 fourcc 解码。** KWin 的输出缓冲在软件合成下是
> `AR24`（8 位），在 GL 路径下是 `AR30` / `AB30`（**ARGB2101010 / ABGR2101010，
> 10 bit/通道**）。早先按 8 位 XRGB8888 硬解 10 位缓冲，会得到满屏**假竖条纹**，
> 看着像画面坏了，其实只是解码错了。现在的 `tools/probe/fbdump.c` 支持
> `AR24/XR24/AB24/XB24/AR30/XR30/AB30/XB30`。

### 接管后设备反复重启 / 内核 panic

**先别怀疑外因**，对照实验：完全不碰接管、设备静置几分钟，uptime 是稳定增长的；
而每次 `enter` 之后必然重启 ⇒ 就是我们自己把内核搞 panic 了。

取证（ramoops 会被 ECC 打乱，按可打印 ASCII 串找）：

```sh
strings /sys/fs/pstore/console-ramoops-0 | grep -E 'Kernel panic|cpufreq_panic_callback|Fatal exception'
```

看到 `cpufreq_panic_callback`（只有 panic 路径才调用）+ `Kernel panic - not syncing:
Fatal exception` 就实锤了。再看 panic 任务是不是显示线程
（处理 `_sde_kms_drm_check_dpms` / panel notifier 的那个）。

已知的触发条件，按 SDE 的硬约束来：

| 现象 | 原因 |
|---|---|
| 4 平面、目的 `0,800,0,800` | `_sde_crtc_validate_src_split_order` 拒（见下） |
| 4 平面、目的 `0,800,1600,2400` | 提交能过、`mode_valid=1`，但 ~20s 后内核 `BUG()` → panic |
| **2 平面、目的 `0,1600`** | ✅ 唯一同时满足两者的形式 |

两条硬约束：

1. **`_sde_crtc_validate_src_split_order`**（`sde_crtc.c`）会把同一 stage 的平面
   **按 `CRTC_X` 排序后配对相邻两个**，要求目的坐标严格递增。所以安卓自己的
   `0,800,0,800` 反而会被拒，报错长这样：

   ```
   _sde_crtc_validate_src_split_order: invalid coordinates, stage:0 l:0-800 r:0-800
   ```

   ```sh
   dmesg | grep -c src_split_order      # 应该是 0
   ```

2. **单条 DSI 链路的本地地址范围只有 0~1600。** 目的坐标写到 1600~3200
   会超出这个范围 —— 提交阶段不报错，但会在二十秒后 panic。

所以设备适配层是 `DEV_KWINWRAP_SPLIT_PLANES="131,127"` +
`DEV_KWINWRAP_SPLIT_DST_INTERLEAVE="0"`（2 平面 × 1600、目的单调）。

### 平面属性：必须补上安卓在设的那 4 个非 ATOMIC 属性

拿 `kmsdump` 逐条比对安卓正在用的平面，安卓显式设了这 4 个，我们一个都不能少：

| 属性 | id | 值 |
|---|---|---|
| `blend_op` | 102 | `1`（opaque） |
| `alpha` | 95 | `255` |
| `zpos` | 94 | `0` |
| `rotation` | 133 | `1`（ROTATE_0） |

它们 flags 里**都没有 `DRM_MODE_PROP_ATOMIC`**，所以塞进 atomic 提交会被判 `EINVAL`；
只能像 `DPMS` / `dsc_mode` 那样走非原子 `DRM_IOCTL_MODE_OBJ_SETPROPERTY`，
且必须在 `DROP_MASTER` **之前**。`alpha` 不设就是 0 = 全透明。

### 面板是 DSC 屏：`dsc_mode` 必须显式打开

内核 cmdline 里 `msm_drm.dsi_display0=...dsc_vid:` ⇒ 面板走 DSC。
`conn67 dsc_mode` 必须是 `1 (dsc_enabled)`，而且它是**非 ATOMIC** 属性
（同样要在 `DROP_MASTER` 前写）。`bpp_mode` 保持 `0`。

### 逐帧调试痕迹怎么打开

`FBSCAN` / `DROP-CAND` / `NOACTIVE` / `EVDROP` / `BUILT` 这些每帧都打的痕迹
默认是**关**的（正常跑会把 `kwinatomic.log` 撑到几十 MB）。
真机上接不了调试器，所以没删，按需打开：

```sh
KWINWRAP_TRACE=1 ...        # 或者在设备适配层加 DEV_KWIN_ENV="KWINWRAP_TRACE=1"
```

`SPLIT:` 行是低频心跳（前 5 帧 + 之后每 64 帧一条），一直开着。

## 触摸不工作

### 手指位置和画面对不上

坐标系要校准。先留空 `DEV_TOUCH_CALIB` 跑通，再调矩阵 ——
见 [适配新设备.md 第 7.2 节](适配新设备.md#72-坐标系)。

快速判断转了 90°：跑 `bin/touchtest`，手指从左下划到右上，
如果圆从左上划到右下，就是转了 90°。

### 完全收不到触摸

```sh
# 按名字找节点（不要用 eventN，每次 boot 都变）
grep -B2 -A5 -i '<你的 DEV_TOUCH_NAME>' /proc/bus/input/devices
```

> ⚠️ **不要对触摸节点跑 `getevent` 旁听。** 多次实锤：这会在某些厂商设备上
> 触发安全联动**直接断网**。要验证触摸请用 `bin/touchtest`。

如果节点存在但 KWin 收不到，可能是 libinput 不认我们 `mknod` 出来的节点
（缺少完整 udev 属性）。用 `touchinj` 绕开 libinput 验证合成器链路：

```sh
WAYLAND_DISPLAY=taketest bin/touchinj 30 /dev/input/eventN
```

`touchinj` 走 KWin 的 `org_kde_kwin_fake_input` 协议直接注入。
它工作但真手指不工作 ⇒ 问题在 libinput/udev 那一层，不在合成器。

## 网络

### 有 IP、ping 通网关、外网不通

接管后 `netd` 被停，安卓那套 per-interface 路由表 + fwmark 没人维护，
一路落到 `32000: from all unreachable`。

```sh
ip rule show
ip route show table <你的 DEV_ROUTE_TABLE>
```

需要一条独立表 + 一条 rule，优先级夹在 31000 和 32000 之间。
见 [适配新设备.md 第 6 节](适配新设备.md#6-网络)。

**网络失败不该阻塞你** —— 它是纯尽力而为的，屏幕已经归 Linux 了。

### ⛔ 踩了红线：`ip link set wlan0 up` 之后 adbd 死了

```
cnss: Failed to start MHI err=-110
Recovery is already in progress → ASSERT 2436
```

**只能长按电源强重启。** 这条路径没有恢复手段 ——
网卡固件进了 recovery 状态，adbd 已经死了，没有通道能救。
所以脚本里永远只做 add-only，绝不 `up`。

### 接管几分钟后 WiFi 掉、UI 崩

看门狗没解除武装。SF 停约 120 秒后 `system_server` 的 watchdog 线程会杀掉
`system_server`，init 级联 SIGKILL `wpa_supplicant`/`netd`/`zygote`。

```sh
adb shell settings list global | grep -iE 'watchdog|nativehang'
```

填 `DEV_WATCHDOG_DISARM` / `DEV_WATCHDOG_REARM`，见
[适配新设备.md 第 5 节](适配新设备.md#5-解除安卓稳定性守护不做的后果很严重)。

> ⚠️ 如果你的 `REARM` 写错了，这些设置会**永久残留**在安卓上
> （参考实现就有这个缺陷）。改完请确认 `desk-stop.sh` 跑完能还原。

## 回不去安卓

### 点了「返回安卓」没反应

链条有三段，逐段查：

```sh
# ① 请求文件写出来了吗（容器侧）
#    会合目录在容器里是 /var/lib/droid-drm-takeover，
#    在安卓侧就是 <rootfs>/var/lib/droid-drm-takeover
su -c 'ls -l /data/local/Droidspaces/Containers/DEBIAN/rootfs/var/lib/droid-drm-takeover/exit.request'

# ② 守护在跑吗（安卓侧）
su -c 'sh /data/local/drm-takeover/android/exit-watch.sh status'
#    期望输出：running pid=<n>

# ③ 设备适配层认对了吗
su -c 'sh /data/local/drm-takeover/core/switch.sh status'
```

> 会合目录里应该能看到 `enter.request` / `exit.request`（容器写）、
> `enter.result` / `device` / `serial` / `heartbeat` / `session.report`（安卓写）。

② 没在跑就启动它，或者装开机自启：

```sh
su -c 'sh /data/local/drm-takeover/android/exit-watch.sh start'
su -c 'sh /data/local/drm-takeover/android/boot-install.sh install'
su -c 'sh /data/local/drm-takeover/android/boot-install.sh status'    # 复核
```

> **开机自启必须装。** 参考实现里这一步要用户手敲命令，不装的话重启后守护
> 没在跑，容器里那个按钮点了永远没反应。本项目做成了
> `boot-install.sh install` 一条命令。
>
> ⚠️ **本机 KernelSU 不执行 `/data/adb/service.d/`。** 实测
> KernelSU 4.2.0-72-g223897c7（uapi 5）：hook 装好、755、重启后**完全没被执行**，
> `/data/adb/ksu/` 下连 service.d 目录都没有，ksu 日志里也没有痕迹。
> 所以主路径是 **KernelSU 模块**
> `/data/adb/modules/drm-takeover-exit-watch/`（`module.prop` + `service.sh`）——
> 同机 `droidspaces` 模块的 `service.sh` 是正常执行的，可以照抄这个形式。
> service.d 那份仍然装（Magisk 与部分 KernelSU 版本认），装了不亏。
> 装完用 `ksud module list` 确认模块 `enabled: true`。
>
> ⚠️ **`service.sh` 的 stdout 会被 KernelSU 吃掉，日志必须自己落盘。**
> 不落盘的话"模块没跑"和"模块跑了但守护自己退了"根本分不清。
> 现在会写 `/data/local/drm-takeover/logs/boot-autostart.log`。
>
> ⚠️ **开机时有三个启动器**都会跑 `exit-watch.sh run`：KernelSU 模块、
> service.d hook、APK 的 `WatchService` 前台服务。它们几乎同时起来，
> 所以单例判据必须是**原子锁**（`mkdir`），不能是"扫 /proc 数进程" ——
> 后者会被自己的 fork 干扰，三个启动器互相看到对方然后**全部退出**，
> 一个守护都不剩，而日志里每个都写着"已在跑"。
> 这个 bug 只在开机路径上暴露，手动从 adb shell 起永远复现不出来。

### 守护在跑，但设备不重启

```sh
# 只有这个有效
adb shell su -c '/system/bin/reboot'
```

`svc power reboot` 和 `setprop sys.powerctl reboot` 都是**静默 no-op** ——
不报错，也不重启。脚本已经用对了。

### 回安卓后卡开机界面 / 不定时重启 / pogo 键盘不认

这是**原地恢复**的已知代价，不是 bug。停容器 ≠ 恢复：
容器启动破坏了安卓 ueventd 的 netlink，热插拔节点建不出来。

正常路径是整机重启。如果你用了 `display/desk-stop.sh`（原地恢复），
接受这个后果或者再重启一次。

## 桌面里的小问题

### 任务栏点不开应用

`xdg-desktop-portal` 必须带 `XDG_CURRENT_DESKTOP=KDE` 起来才有 KDE 后端。
`drm_start_desktop()` 已经处理。

### X11 应用全部起不来，Wayland 应用全好

KernelSU 的 enhanced_security 把 Xwayland 的 `PrivsElevated()` 里那次
`seteuid(0)` 试探当成提权攻击直接 SIGKILL 了。

设 `DEV_NEEDS_KSU_XWL_SHIM=1`（本机 OPD2511 已设）。

### 中文输入法选词只剩前缀字母

双桌面共享 HOME 的坑。DRM 桌面要求 Qt 直连合成器 text-input，
为此删了全局 `/etc/environment` 的 `QT_IM_MODULE=fcitx5` ——
而帧转发方案的安卓 IME 桥恰恰依赖 Qt 走 fcitx5 桥。

修复 = 在需要 fcitx5 的那一侧**会话级**注入，全局保持干净。

## 拿不到任何信息时

```sh
# 把现场全抓下来
adb shell su -c 'sh /data/local/drm-takeover/display/drm-diag-once.sh'
adb pull /data/local/drm-takeover/run/logs/drmdiag/
adb pull /data/local/drm-takeover/run/logs/
```

`display/dmesg-harvester.sh` 在接管期间每 20 秒收割一份安卓 dmesg
（保留最近 15 份）—— 断流/重启会清掉设备侧的 ring buffer 和 pstore，
只有提前落盘才能留下崩溃前的现场。

```sh
setsid nohup sh display/dmesg-harvester.sh &
```
