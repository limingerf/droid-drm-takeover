# 屏幕键盘一闪一闪（拖影）—— 两个输入法抢焦点

> 结论：容器里同时跑 **fcitx5** 和 **maliit-keyboard** 两个输入法，它们对同一个
> 文本框同时响应，焦点在「文本框 ↔ 键盘」之间无限来回跳，键盘就在
> **显示/隐藏之间反复横跳**。表现就是用户说的「拖影还会一闪一闪的」。
> 修法：**默认只跑 maliit，不跑 fcitx5**。

## 1. 症状

用户的原话，按时间顺序：

| 阶段 | 描述 |
|---|---|
| 最初 | 「屏幕键盘弹出的时候底部在刚打开的时候有拖影像是渲染错误」 |
| 杀掉重复实例后 | 「键盘能弹，但拖影还在」 |
| 净化环境变量后 | 「仍然有一层拖影在任务栏那，只有刚弹出的时候那几秒会有，之后消失」 |
| 改完面板占位后 | 「没变化」 |
| 关掉 slide 特效后 | 「拖影还会**一闪一闪**的」 |

「一闪一闪」这个词是转折点 —— 它不是滑动残影，是**周期性重复**。

## 2. 证据

### 2.1 kwin.log 里键盘报告的几何在交替

```
$ grep -a 'keyboard is reporting' kwin.log | tail -20
keyboard is reporting <x y w h>: < 0 571 1600 429 > to the app manager.
keyboard is reporting <x y w h>: < 0 562 1600 438 > to the app manager.
keyboard is reporting <x y w h>: < 0 952 1600 48 >  to the app manager.
keyboard is reporting <x y w h>: < 0 562 1600 438 > to the app manager.
keyboard is reporting <x y w h>: < 0 571 1600 429 > to the app manager.
...
```

高 `429` = 键盘展开，高 `39`/`48` = 键盘收起。两者**交替出现**，就是肉眼看到的闪。

全部 309 次报告的分布（`sort | uniq -c`）：

```
 89  < 0 562 1600 438 >
 81  < 0 610 1600 390 >
 41  < 0 1000 1600 0 >      ← 完全收起
 32  < 0 952 1600 48 >
 22  < 0 571 1600 429 >
 ...
```

### 2.2 输入法上下文在无限重建

```
$ grep -ac 'zwp_input_method_v1_activate'   kwin.log   → 82
$ grep -ac 'zwp_input_method_v1_deactivate' kwin.log   → 80
$ grep -ac 'InputMethodContext::~InputMethodContext'   → 80
$ grep -ac 'zwp_input_method_context_v1_'              → 2160
```

日志尾部是一个**自动重复、无需用户操作**的闭环：

```
deactivate → ~InputMethodContext → 报告 <0 961 1600 39>   (收起)
→ activate → InputMethodContext()  → 报告 <0 571 1600 429> (展开)
→ surrounding_text → preferred_language → content_type → commit_state
→ deactivate → ~InputMethodContext → 报告 <0 961 1600 39>
→ …
```

### 2.3 判决实验

停掉 fcitx5，等 30 秒，数日志增长：

```
=== 停掉 fcitx5 之前 ===
  keyboard is reporting 次数 = 309
  activate 次数            = 82

=== pkill -x fcitx5，等 30 秒 ===
  keyboard is reporting 次数 = 309   （基线 309，增长 0）
  activate 次数            = 82   （基线 82，增长 0）

  ★★★ 循环停了 —— fcitx5 就是根因
```

**30 秒增长 0**。根因确定。

### 2.4 而 fcitx5 其实没被任何应用用上

```
$ grep -aE 'IM_MODULE|XMODIFIERS' /etc/environment
  (空)

$ tr '\0' '\n' < /proc/$(pgrep -x plasmashell)/environ | grep -aE 'QT_IM_MODULE|GTK_IM_MODULE|XMODIFIERS'
  (空)
```

中文拼音是 maliit 自己在做 —— maliit-keyboard 包自带 `zh-hans` 插件和
libpinyin 词库，用户已确认「输入法能打字」。所以 fcitx5 在这里纯粹是负担。

## 3. 机理

```
   应用文本框获得焦点
        │
        ├──► KWin 通过 zwp_input_method_v1 给 maliit 发 activate
        │        → maliit 弹出屏幕键盘（报告高 429）
        │
        └──► fcitx5（装了 fcitx5-module-wayland）也走 Wayland 输入法协议
                 → fcitx5 弹出自己的候选窗 → 候选窗抢走焦点
                          │
                          ▼
             KWin 给 maliit 发 deactivate → 键盘收起（报告高 39）
                          │
                          ▼
             焦点回到应用 → 又 activate → 无限循环
```

关键点是 `zwp_input_method_v1` 本身是**独占**的（只有 KWin 拉起的那个 maliit
持有它），但 **fcitx5-module-wayland 让 fcitx5 从另一条路（候选窗 + 客户端库）
参与进来**，两边对同一个文本框同时响应，于是焦点被反复夺走。

## 4. 修法

`core/lib/display.sh` 改两处，**默认都不启用 fcitx5**：

1. **不注入 fcitx 环境变量**。默认走
   `-u QT_IM_MODULE -u GTK_IM_MODULE -u XMODIFIERS -u SDL_IM_MODULE -u GLFW_IM_MODULE`，
   让应用用 Wayland 输入法协议（KWin + maliit）。
2. **不拉起 fcitx5**。只有 `DEV_IM_FCITX=1` 时才起，并且会打警告。

同时**保留** `pkill -x fcitx5` 那行 —— 上一次会话若留下 fcitx5 进程，
不清掉会立刻开始闪。「清残留」和「不再拉起」两件事都要做。

另外把输入法可用性判据从「fcitx5 或 maliit 有其一」改成**必须有 maliit** ——
触摸屏要的是屏幕键盘，只有 maliit 能弹。

### 要用 fcitx5 的话

必须**同时**满足两条，否则又会开始闪：

1. 设 `DEV_IM_FCITX=1`；
2. 把 maliit 从 `kwinrc` 的 `[Wayland] InputMethod` 摘掉（否则两个继续抢焦点）。

## 6. 排查手法上的教训

1. **「一闪一闪」这个描述比「拖影」信息量大得多。** 「拖影」指向渲染残留，
   「一闪一闪」指向**周期性重复** —— 后者直接把方向从「画面错误」扭到
   「状态机在循环」。用户换了个说法，问题当天就定位了。所以症状描述要反复问、
   要追着用户的原话用词。
2. **数次数比读单行日志有用。** 单看一行
   `keyboard is reporting <0 952 1600 48>` 只会觉得「这个高度奇怪」；
   把它 `sort | uniq -c` 之后，看到 `429` 和 `39` 交替出现，循环立刻现形。
3. **判决实验要做成「数增长」。** 停掉一个嫌疑进程，记下基线，等 30 秒再数。
   `增长 0` 是比「看起来好了」强得多的证据。
4. **要查「这个组件到底有没有被用上」。** fcitx5 装着、跑着，但
   `/etc/environment` 和应用环境里一个 `IM_MODULE` 都没有 —— 说明它没被任何
   应用加载。一个**没被用上却还在跑**的组件，往往就是纯冲突源。
5. **别把「符号看起来像」当成根因。** slide 特效的符号列表极具说服力，
   关掉也确实生效，但症状没走。证据链要闭环到**症状消失**，不是到**改动生效**。
